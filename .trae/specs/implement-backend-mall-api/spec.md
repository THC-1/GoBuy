# GoBuy 商城后端实现规范 (Spec)

## 为什么 (Why)
当前项目已完成前端页面与交互原型，但后端仍是初始骨架，无法支撑登录鉴权、商品管理、购物车、订单流转等真实业务。需要基于已完成的 `frontend` 页面与 `frontend/README.md` 对接说明，补齐一个可联调、可扩展的 Spring Boot 商城后端。

## 做了哪些更改 (What Changes)
- 基于 Spring Boot 3 + MyBatis-Plus + MySQL 8.0 搭建后端基础架构，采用当前常见的分层项目结构。
- 建立统一返回体、全局异常处理、参数校验、JWT 鉴权与基础安全能力。
- 实现后台管理端接口：
  - 管理员登录
  - 用户管理、角色管理、菜单权限管理、数据字典管理
  - 商品分类、属性/规格模板、SPU、SKU、上下架管理
- 实现商城前台接口：
  - 用户注册/登录
  - 首页商品展示、商品详情、评价展示
  - 用户资料、收货地址、收藏夹
  - 购物车、结算、下单、模拟支付、订单状态流转
- 单独创建数据库脚本目录，存放初始化建表与基础数据 SQL，供用户自行执行。
- 提供本地开发所需的 MySQL 8.0 连接配置，默认账号 `root`、密码 `123456`。

## 影响 (Impact)
- 影响的功能：管理员鉴权、RBAC、商品中心、商城用户域、购物车、订单与支付模拟。
- 影响的代码：`backend` 目录下的 Maven 依赖、配置文件、分层包结构、接口实现、持久层映射、测试代码与 SQL 脚本目录。

## 新增需求 (ADDED Requirements)
### 需求：后端基础架构
系统必须提供基于 Spring Boot 3 的常见商城后端分层架构，并使用 MyBatis-Plus 作为 ORM 框架。

#### 场景：初始化后端工程
- **当** 开发者查看后端项目结构
- **则** 可以看到清晰的分层组织，例如 `common`、`config`、`security`、`controller`、`service`、`service.impl`、`mapper`、`entity`、`dto`、`vo` 等职责边界明确的模块

### 需求：数据库与脚本交付
系统必须以 MySQL 8.0 作为关系型数据库，并将建表、初始化字典和演示数据脚本放在独立目录中供用户手动执行。

#### 场景：初始化数据库
- **当** 用户准备本地数据库环境
- **则** 可以在独立 SQL 目录中找到完整的建库建表脚本与必要初始化数据脚本
- **且** 后端配置默认使用 MySQL 8.0、账号 `root`、密码 `123456`

### 需求：统一接口规范
系统必须提供统一返回体与统一异常处理，满足前端 README 中的对接约定。

#### 场景：接口调用成功或失败
- **当** 前端请求任意后端接口
- **则** 成功响应返回统一结构的数据体
- **且** 参数错误、未登录、无权限、业务异常等情况返回统一错误结构与明确提示

### 需求：认证与鉴权
系统必须支持后台管理员登录与前台用户登录注册，并通过 JWT 完成后续请求鉴权。

#### 场景：后台管理员登录
- **当** 管理员提交正确凭据
- **则** 系统返回可用于后续后台接口访问的 JWT

#### 场景：前台用户注册与登录
- **当** 用户完成注册或登录
- **则** 系统返回用户身份信息与可用于前台接口访问的 JWT

### 需求：后台系统管理
系统必须提供与前端管理页面对应的系统管理接口，包括用户、角色、菜单、权限关系与数据字典。

#### 场景：维护系统管理数据
- **当** 管理员访问系统管理相关页面
- **则** 可以完成列表查询、分页、增删改、状态变更及必要的关联关系维护

### 需求：商品中心
系统必须提供商品分类、属性/规格模板、SPU、SKU 与上下架管理能力，并支持前端动态 SKU 页面所需的数据结构。

#### 场景：维护 SPU 与 SKU
- **当** 管理员提交 SPU 基础信息及 SKU 组合数据
- **则** 系统可以保存 SPU、规格值与 SKU 明细
- **且** 商品详情接口可以返回规格列表与 SKU 列表供前端做规格匹配

### 需求：商城用户域
系统必须提供与前台商城页面对应的用户域能力，包括个人资料、地址簿、收藏夹与评价展示。

#### 场景：维护用户个人中心信息
- **当** 已登录用户访问个人中心
- **则** 可以查询和修改个人资料、管理收货地址、查看和维护收藏数据

### 需求：购物车与订单流转
系统必须支持基于 SKU 的购物车、订单结算、订单提交流程与模拟支付。

#### 场景：提交订单
- **当** 用户从购物车或立即购买流程提交订单
- **则** 系统根据地址与 SKU 数量生成唯一订单号
- **且** 扣减库存时具备基础并发控制能力，避免明显超卖

#### 场景：模拟支付
- **当** 前端调用模拟支付接口
- **则** 系统更新订单状态为已支付或待发货对应状态，并可供前后端页面查询展示

## 修改需求 (MODIFIED Requirements)
### 需求：前端 Mock 数据对接方式
前端页面当前使用硬编码 Mock 数据，后端实现后需以真实接口替换对应页面的数据来源，并沿用 `frontend/README.md` 中约定的 JWT 与统一返回体模式。

## 移除需求 (REMOVED Requirements)
### 需求：纯前端静态数据驱动
**原因**：当前商城流程仅依赖页面内 Mock 数据，无法完成真实联调、持久化与业务流转。
**迁移方式**：逐步将各页面中的静态数据替换为对应后端接口调用，并按模块完成联调验证。
